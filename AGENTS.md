# FITDLE — Agent & Maintainer Notes

Engineering handoff for people and coding agents. The public introduction and
hosting guide is [README.md](README.md) (English, default) with the Chinese
translation [README.zh-CN.md](README.zh-CN.md).

**Quick orientation**
- Puzzle: guess the victim hull of a real zKillboard killmail from staged clues.
  Gameplays: Standard, Fitting Audit, Timed; Arbitration in rooms only.
- Front end: static ES modules (`index.html`, `js/`, `styles/`), no bundler.
  Back end: `server/` (Node 24, Fastify, WebSocket, `node:sqlite`).
- Build: `prepare:sde` → `build:catalog` → `build:killpool` → `build:weights` →
  `build`; tests: `npm test` and `npm run test:server` (see *Commands*).
- Rules below are grouped: hard rules first, then architecture, game rules
  (target, KB, reveal), runtime/API, UI copy, and CI/deployment.

## Non-negotiable rules

**Secrecy**
- Never reveal today's target ship, killmail ID, victim name or answer render in
  tests, logs, commits, screenshots or chat. Use non-target/public data in screenshots.
- Never commit `.env`, `.cache/`, `dist/`, `data/`, browser profiles, databases or
  any token. `API_CONTACT` and SSO secrets are runtime-only.

**Versioning and release**
- Every code change gets a **patch** bump (the pre-commit hook does it). Never
  bump `minor`/`major` unless the owner asks. Docs/CI-only commits may skip it
  (`VERSION_BUMP=none` or `--no-verify`).
- Before every commit run `npm test` and `npm run test:server` (run
  `npm install --prefix server` first) and make sure they pass. Before opening a
  release PR also run the full build (`npm run build`) and both suites. If the
  environment cannot run something, say exactly which checks did not run in the
  report so the owner can run them locally; never claim untested work passes.
- Work happens on the local `dev` branch. Ordinary commits may be pushed to
  `github/dev` (no CI runs there). Open/merge PRs into `main`, tag, release,
  publish Pages or images only on an explicit request. Never commit on `main`.
- `CHANGELOG.md` is written (in Chinese) only at a release, which squashes the
  pending local commits into one release commit. See *Release notes*.

**Product scope**
- Keep the puzzle deterministic for every player: fixed online Daily target,
  stable hull/page hashes, completed-month record selection.
- The Node service is the only backend (EVE SSO, targets, stats, rooms). No other
  accounts, second runtime database, public leaderboard, or third-party
  signaling/relay service without an explicit request. zKill/ESI/EVE images and
  the vendored dogma engine are data dependencies, not services.
- Prefer official SDE/zKill/ESI/image sources. Do not cache images in the repo.
- Do not hard-code deployment domains in authored JS/CSS/HTML. Use
  `manifest.links` or the runtime location; share OG images use `PUBLIC_ORIGIN`
  (CI fallback `PAGES_URL`, then GitLab's `CI_PAGES_URL`).

**UI and copy**
- Follow EVE Photon UI: dark compact panels, fine borders, clear hierarchy. Do not
  add effects or decoration that were not requested; remove rather than add.
- Interface strings live in `js/messages/<locale>.js`, one flat file per language
  with identical keys. Terms and sources are in `docs/i18n-glossary.md`.
- Localization priority: official EVE localization, then community wording, then
  own translation. Never translate EVE terms/names/official strings; record
  ambiguous terms in the glossary.
- The README exists in two languages: `README.md` (English, default) and
  `README.zh-CN.md` (Chinese). Every README change updates both in the same
  commit, with the same sections, links and image. Both keep the
  `English | 简体中文` switch at the top.

## Architecture

- Static ES modules in `js/`, `styles/`, `index.html`, assembled into `dist/`
  by `scripts/build-dist.mjs`; no bundler.
- A lightweight Node service in `server/` provides EVE SSO sessions, online
  Daily/random targets, run/stat recording, and authoritative WebSocket rooms.
  It can serve `dist/` and `/api`/`/ws` from one origin.
- Online Daily is server-pinned once per game day and cached in SQLite. Online
  Standard/Audit/Timed get a server-issued random target per run; practice gets
  a client random/explicit KB target and never scores.
- `data/manifest.json` is generated by `scripts/build-catalog.mjs`; it contains
  pools, links, data version, SDE release/build, zKill snapshot, version and
  optional `apiBase` (only when `API_ORIGIN` differs from `PUBLIC_ORIGIN`).
- `data/catalog.json`, `data/refs/*.json`, `data/killpool.json` are generated.
- `dist/` contains authored `js/`, `styles/`, `assets/`, generated `data/`, and
  `vendor/dogma-engine/`.
- Build-time configuration lives in ignored `.env` (see `.env.example`), with
  environment variables taking precedence. The Node service loads the same root
  `.env`; `PUBLIC_ORIGIN` / optional `API_ORIGIN` derive callback, CORS, cookie
  security and share URLs.

### Online service and multiplayer

- `index.html` is the only app entry. `js/main.js` boots the puzzle; `js/api.js`
  talks to the same-origin service; `js/rooms.js` embeds the room view into the
  main shell and hands Arbitration to the single-player hero/dossier.
- `server/` is Node 24 + Fastify + `@fastify/websocket` + `@fastify/cookie` +
  `@fastify/static` + `jose` + built-in `node:sqlite`. It serves `dist/`, `/api`
  and `/ws`; a split deployment sets `API_ORIGIN` and derives CORS/callback.
- EVE SSO is authorization-code + PKCE, state/JWKS validation, minimal
  `publicData` scope. Only the `name` and character-id (`sub`) claims are used.
  Accounts are keyed by
  normalized character name; alts are separate; character rename creates a new
  account. The character ID is stored only to render the official EVE portrait;
  no corporation, alliance, avatar image or other identity data is stored.
  The token endpoint is read from the SSO metadata document; the client secret stays
  server-side and the callback is `${API_ORIGIN || PUBLIC_ORIGIN}/api/v1/auth/eve/callback`.
- Modes are determined by auth/back-end availability: guest or service failure is
  Practice; logged-in is Online. Mode is not a manual toggle. Practice provides
  Standard/Audit/Timed, random or explicit KB, no scoring. Daily is online-only.
- Online Daily is pinned once per game day and cached in SQLite. Online
  Standard/Audit/Timed get a server-issued random target per run. A current KB
  entered from a share link becomes an online custom run when logged in; custom
  runs can be played and resumed but never enter streaks, win days or target stats.
- The service records solo guesses: `POST /online/runs/:id/guess {shipId}` counts,
  deduplicates and judges them; `finish` only accepts a Timed loss. A run counts
  from its first guess, a Timed run from starting the clock (`begin`). `start` returns the player's open run of that gameplay, so a
  reload, a closed page or another device continues it. `abandon` (NEW TARGET, after
  a confirmation) loses a started run and forgets an unstarted one; a started run
  unfinished for 24 hours is lost. NEW TARGET is disabled while a random Timed target
  waits for its clock: it shows no clue yet. Explicit `kb` targets can be left.
- `js/run-sync.js` delivers solo guesses in order, keeps unsent ones in
  `fitdle:v1:pending-runs` and retries; resending is harmless.
- Room guesses go through `raceGuess {roundId, shipId}`; the server counts, judges
  and keeps the Timed cooldown, and answers the player with `raceGuesses`.
  `raceResult` only reports a Timed loss. Leaving for good (or the grace ending)
  during a running round is a loss of that round; being kicked is not.
- Clients submit full hull names or ship ids. `js/ship-query.js` resolves
  abbreviations and partial names and asks when several hulls fit; the server never
  accepts abbreviations.
- The room state API answers players of the room only. Scores reset only between
  matches. Seated players rejoin without the password; empty passwords are no guess.
- Requests are limited per player (`server/src/limits.mjs`). Logs carry paths without
  query strings, and the SSO state is bound to the browser by a short-lived cookie.
- `FITDLE_DEV_AUTH` is ignored in production unless `PUBLIC_ORIGIN` is loopback.
- zKillboard killmails lose `attackers` on arrival (`js/killmail.js`); nothing uses it.
- `multiplayer` is a separate room surface behind login. A room has no default
  gameplay/rule; the owner selects Standard/Fitting Audit/Timed (same-file race) or
  Arbitration and settings before a match and again between
  matches. Players are retained; scores are room-cumulative and the owner can
  reset them. Daily cannot be selected in a room.
- Arbitration is dealer-rotation: six small rounds per dealer stint, no timer. An Arbitration
  room can run 1..N **big rounds**, where one big round is one pass through the
  active dealer order. The small-round rules are fixed; only the big-round count
  is host-configurable. The dealer publishes at least one unpublished clue per
  round (or all), and at least one with weight while any weighted clue is still
  selectable (`clue-weight-required`); active players guess once. If every clue
  is published, players keep guessing each round. The stint ends after six
  rounds or when every player still in the room has solved.
- Arbitration scoring lives in `js/mp/rules.js` (`ARBITRATION_SCORING`, shared by
  server and dossier preview). f = published share of the total clue weight
  after the dealer publishes; n = players at stint start (fixed). A solve in
  round k pays `solveBase*(1-f)+solveEarly*(7-k)` at once. After each round
  every unsolved player gives the dealer `dealerRound*f`; when the stint ends
  (six rounds, all solved, dealer leaves or host ends) the dealer gets
  `dealerEnd*n*f`. The dealer total is the raw sum / n, credited with cumulative
  rounding (`arbitrationDealerCredit`). A player who leaves stays unsolved to the
  end of the stint and keeps earned points; a solved leaver stays solved. Leaving
  dealer / host end settle the current round and the end bonus before
  `matchResult`. When the scheduled dealer is gone, the next connected pilot in
  the big-round order deals. Scores are room-only, never stored on accounts.
  Clues on the wire carry `p` (share of total weight), never per-player values.
  `arbitration_rounds` stores `published_share` and `unsolved` per round for
  later coefficient tuning.
- Room state, target selection, clue release, guessing, scoring and timers are
  authoritative on the server. Clients never send scores. The server stores
  target exposures/runs/rounds for future statistics; no leaderboard UI/API yet.
- `ROOM_MAX_PLAYERS` controls total room seats (default 8, allowed 2..32,
  including spectators/offline seats). Existing names rejoin without consuming
  a new seat.
- `ROOM_ARBITRATION_BIG_ROUNDS` / `ROOM_ARBITRATION_MAX_BIG_ROUNDS` define the Arbitration default and
  host limit for big rounds. `ROOM_TIMED_DURATION_MINUTES` /
  `ROOM_TIMED_MAX_DURATION_MINUTES` do the same for Timed room duration.
- `ROOM_RECONNECT_GRACE_MS` (default 60000, range 5000..300000) keeps a
  disconnected player in the room and the current owner in place until the grace
  ends. Reconnecting restores the same player; only after the grace may the
  player be removed, the owner transferred, or a disconnected Arbitration dealer
  end the match. Explicit leave and host kick are immediate. The Local list shows
  a spinner and `room.reconnecting` while a player is inside the grace.
- Chat is ephemeral, sanitized, length-limited and rate-limited; it is not
  persisted. Chat sends carry a client id, and the server acknowledges success or
  returns a localized rate/validation error. The client keeps the draft until an
  acknowledgement.
- The service owns WebSocket delivery. There is no PeerJS/WebRTC/TURN, no host
  tab dependency, and no iframe race. Session cookie auth is used for WS.
- Room connections: the server pings every 25 s and drops a socket after missed
  answers; the client sends an application `ping` every 25 s, reconnects at once
  after a drop and then backs off. A newer connection of the same player closes
  the older one (4001). Closed sockets are logged without names, chat or targets.
- Asynchronous target loads go through `loadMatch`; check `current()` before
  touching the room. Only one load runs per room, and ending the match cancels it.
- The owner is always a player in the room (`ensureOwner`). Players who never
  connect leave after the reconnect grace. Arbitration progress after a leave,
  timeout or dealer return goes through `checkArbitrationProgress`.
- Room messages and wrong room passwords are limited per player.
- `js/rooms.js` panels are skeletons of regions; update regions, never replace a
  panel. The chat input, open selects and running holds must survive updates.
- A round result is kept until the server confirms it and is resent on reconnect.
- Room chat is presented as the Subspace Communication Beacon. Use the exact
  English name/source string and localized equivalents in `js/i18n.js`.
- When the room socket is not connected, show the localized
  `room.chatUnavailable` system line and keep the chat input disabled.
- The Daily reset CTA is enabled only after the local countdown has crossed into
  a new game day; clicking it reloads into the new Daily target.

## Data flow

1. `prepare:sde` calls the official SDE HTTP API (`sde.evetech.net/tranquility/latest/`),
   downloads the release-specific JSONL tables whose version changed into
   `.cache/sde-source/`, reuses the rest, and normalizes them.
2. `build:killpool` builds a small offline fallback pool from zKill global losses
   and stores zKill's server `Date` as `serverDate`.
3. `build:weights` fetches zKill `stats/shipTypeID/{id}/kills/` for missing or
   aging hulls and stores recent/all ship-loss counts with a per-hull fetch time
   in `.cache/ship-weights.json`. Entries expire after 7 days; from day 5 a build
   renews up to 60 of the oldest. A failed request keeps the previous value and
   never writes zeros, which would drop the hull from the pools.
   zKill's `rankings.recent` bucket is the 90-day window. Economy clues use
   `losses90`, recent kill rank (`shipsDestroyed`), and a recent
   kill/(kill+loss) danger index. The block title, not each row, says 90 days.
4. `build` reads normalized SDE + weights + killpool and writes `data/` and
   `dist/`. It also emits a compact `data/module-fallback.json` from
   `typeDogma` for the six attributes used by the audit fallback simulator, so
   that fallback never calls ESI at runtime.
5. Online runtime: the service reads the server game day, resolves a Daily target
   once (HMAC server seed, build-time pools, zKill loss pages), caches the
   killmail, and serves it to logged-in clients. Online Standard/Audit/Timed get
   a server random target per run. Practice uses client random/explicit KB only.
   No local clock or static target is used for online Daily.

## Target selection

- Eligibility: all SDE hulls except those with zero all-time zKill losses
  (special/ceremony hulls).
- Standard: mild high-usage preference:
  `1 + 2.2 * log1p(recent)/log1p(max)`.
- Audit: mild low-usage preference:
  `1 + 1.8 * (1 - normalized)`.
- Pools are fixed at build time: `normalShipPool`, `auditKillShipPool`. Repeated
  IDs are integer weights.
- Online Daily seed: HMAC(server secret, gameDay, algorithmVersion).
  `dataVersion` is never part of the daily seed.
- Ship: weighted rendezvous order over the mode pool. Each unique ship keeps its
  best copy score; ships are sorted by score with numeric ship ID as the tie-break.
  Later items are the deterministic fallback queue. No floats, array order or usage stats are consulted.
- Online Standard/Audit/Timed use a server-issued random target per run; practice
  uses a client random/current KB target. Only Daily has a fixed daily KB.
- The target continues to rotate every game day even if the site is not rebuilt;
  SDE and weight changes only apply after a rebuild.

## KB selection

- The game day boundary is build-configurable (`FITDLE_GAME_DAY_START_UTC`);
  default `11:00` UTC.
- Daily target times are sampled from `FITDLE_KB_SELECTION_START_DATE` to the last
  day of the most recent complete month. The sample uses a truncated exponential
  recency distribution with `FITDLE_KB_RECENCY_HALF_LIFE_DAYS`.
- Ships come from one deterministic weighted queue over the full mode pool, seeded
  by the server Daily HMAC seed. Only a ship with no usable kill advances to the
  next queue entry.
- Ship loss pages use `/api/losses/shipTypeID/{id}/page/{page}/`; these pages span
  months, so low-volume ships do not produce empty-month requests.
- Page 1 is the latest 200 losses. A page shorter than 200 is the whole history.
  A full page is followed by page 2, 3, ... until the page covers the sampled
  target time, the history ends, or `FITDLE_KB_MAX_SCAN_PAGES` is reached.
- The selected page is filtered by `victim.ship_type_id`, the KB lower bound, the
  complete-month end, and `allowEmptyKb`. The closest kill to the sampled target
  time wins; equal times use a deterministic hash tie-break.
- If the scan cap is reached before the target time, no extra page is requested;
  all already-loaded pages are combined and one kill is chosen with a deterministic
  recency-weighted draw.
- The personal `allowEmptyKb` setting applies to random targets: practice filters
  in the browser and online runs send `allowEmpty` to `/online/start`. Daily,
  rooms and explicit `kb` targets are shared or chosen, so they ignore it.
- Service random targets use the complete killmail from the loss page (no
  `killID` request) and keep five ready killmails per hull. The compressed page
  stays cached for its upstream lifetime and is never requested again before; the
  browser uses the killmail the service sent.
- `TARGET_SPARES` (default 2, 0..8) random targets per pool and empty-hull choice
  are prepared after that pool's first use. They follow the same selection rules,
  are handed out once and expire after an hour.
- Every ship page is reused for the hour zKillboard allows, keyed by ship and page.
  Failures are not cached. A page 100 scan is the absolute API limit.
- `FITDLE_KB_SELECTION_START_DATE` is a global lower bound for all modes.
  Explicit `?kb=` links bypass it.
- A network/API failure aborts selection; an empty page advances to the next ship.
  Never use the static kill pool, SDE-only dossier, local clock, another day or
  another ship.
- If every queued ship has no candidate, show the localized NO TARGET screen with
  Free mode. Free random targets respect the KB lower bound; explicit `kb` links
  do not.
- There is no archive mode; historical-day consistency is intentionally not
  supported. Only the current game day is synchronized.

## Reveal rules

- Every answer builds one immutable `revealPlan` at `buildAnswerData()` time:
  opening queue plus per-category queues. Queue order is a weighted random
  permutation (low weights more likely early, never a strict weight sort).
- Queue seeds use the server target seed for Online and the stable KB seed for
  Practice, then add mode, timed/standard and queue name. Guesses are never part
  of a seed.
- Opening: budget 9, max weight 13, min 3 / max 7 clues, candidate floor 6; no
  cargo and no bonus in Standard opening, no tagged equipment, one identity and
  one equipment.
- Standard only: guesses reveal shared static values. Bonus clues are never
  proactively revealed; they match only on the same `termKey`
  (`section|normalizeBonusKey(text.en)`), regardless of numeric value/unit. All
  target bonuses sharing that term are revealed.
- Standard misses: equipment queue consumes its weight budget
  (`base + floor(equipmentCount / divisor)`, capped); cargo queue consumes its own
  independent weight budget. Guessed/already-revealed clues skip without cost.
- Audit: no guess matching. Equipment queue gets `miss` per miss; other queue gets
  `1 + ceil(shortfall / 2)`; cargo gets `max(1, ceil(cargoCount / divisor))`.
  Equipment shortfall transfers to the other queue; cargo/other exhaustion does
  not invent new transfers.
- Timed: one mixed queue, no guess matching; each release consumes the original
  `1, 1, 2, 2, 3, 3...` quota. Opening uses the same opening queue.
- Reveal growth must be monotonic: later rounds only append; a previously shown
  clue never disappears.
- All fitted modules are simulated as online and active, never overheated; cargo,
  fuel and spare fighter-bay modules stay offline. Audit simulation keeps only
  one propulsion module (larger size first, then Microwarpdrive over
  Afterburner) and simulates cloaking devices online but inactive.
- Audit static weights start from base stats (so fitted values do not inflate
  weight), then a clue whose fitted value differs from the **all-V no-modules
  baseline** is multiplied by 0.7. Skill-only changes do not reduce weight; only
  module effects do. `calculateDogmaBaseline` supplies that baseline.
- Equipment parsing keys by `module type + slot`; a battery fitted in mid and also
  carried in cargo must render as two lines with their own quantities.
- Fighter tubes (158..161) are `fighter`; flag 155 is `fighterBay` and flag 133 is
  `fuelBay`. Only category-87 fighters stay in fighter slots; spare modules,
  charges and scripts there are cargo.
- Standard mode always includes structure resists in the opening clues and gives
  them weight 0 because every hull has the same base structure resists.
- Audit resistance clues follow the fitted resist gear, not only the base hull
  profile. No resist gear, or only a plain/T1/T2 damage control, caps the clue
  low because calculated values are shared; faction+ damage controls and any
  resistance module floor the clue to at least that module's weight; Assault
  Damage Controls raise it sharply (structure at least 9.5, shield/armor at
  least 8.8); non-uniform structure resists (audit weather) reach 9.8.
- Faction+ damage controls and resistance modules receive an 8.2 equipment
  weight floor; their resistance clue cannot weigh less than the module.
- Sensor strength is one clue. It displays only the sensor type(s) with a
  non-zero value: normally one, in the owning race's colour; two special shuttles
  have all four equal. Shield recharge time is a static SDE clue. In Audit their
  fitted values come from the dogma engine; shield recharge is stored/displayed
  in seconds. Drone bay/bandwidth zero always renders as `0`, not a “No drone
  bay” label.
- Low-slot weapon upgrades are weighted by the weapon family they improve
  (projectile/energy/hybrid/missile/drone/disintegrator/turret); matching fitted
  weapons raise weight from 5.8 to at least 7.4.
- Limited modules get a scarcity bonus from how many catalog hulls their
  `fitRestrictions` cover: fewer compatible hulls = higher weight.
- All fitted modules on Corvettes (group 237) and Zephyr (group 1022) are treated
  as limited and weighted accordingly, because those hulls carry built-in gear.
- Fighters are `limited` and weigh 10; Excavator/Pluto/special mining drones are
  `unique` and weigh 10. Jump fuel weighs 10.
- Rigs weigh at least 8.5; large/capital rigs reach 10.
- All equipment weights are clamped to 1..10, matching the x/10 UI.
- Equipment size adds weight: Capital/XL +7, Large +2.2, Medium +0.8.
- Ship bonuses use structured SDE entries: section (role/types), skill type ID,
  importance, numeric bonus, unit ID, localized text, canonical term key, and
  exact term+value key. Never identify a bonus by array index or `importance`
  alone. Rebuild these keys from raw SDE whenever the SDE changes.
- Bonus term identity is section + normalized English text. Exact-value identity
  adds the numeric bonus and unit. More ships sharing a term lowers weight; if
  the value is shared too, lower it further. Distinct values add weight by their
  normalized spread. A unique term is weight 10 and tagged `unique` like
  equipment. Role bonuses are always `limited`; skill bonuses that target a
  race/class are also `limited`. All `limited` bonuses get a weight increase,
  and role bonuses have a higher floor.
- Equipment restriction markers describe the SDE restriction shape, not hull
  count: one `shipGroups` entry or one `shipTypes` entry → `unique`; multiple
  groups/types → `limited`; no restriction → no marker. A unique equipment clue
  weighs 10; limited clues use breadth scarcity.
- Bonus `showinfo` module links carry `links` IDs into the catalog. A bonus
  inherits its linked equipment's marker: one restriction group/type makes the
  bonus `unique` and weight 10, multiple groups/types make it `limited`, and
  unrestricted equipment contributes no equipment-derived marker. Limited
  equipment and its bonus use the same breadth-based rarity weight, so rarer
  restrictions raise both. Assault Damage Control has two groups and is limited;
  Bastion modules have one Marauder group and are unique. Mining-laser/Strip
  Miner bonuses use the same range rule.
- Module metadata includes `requiredSkills`. A bonus linked to a skill affects
  every fitted module whose required skills include it; a bonus linked to a
  module affects that module and its module group. Affected fitted equipment and
  cargo clues are raised to at least the bonus weight, and high-slot/cargo
  ammunition then inherits the boosted weapon weight.
- Module metadata includes `power`/`cpu` and ships include `rigSize`. A fitted
  module's base PG/CPU requirement infers the smallest hull bracket where at
  least half the ships can fit it; medium/large/capital fits receive a size-based
  weight floor. Cargo spare modules are excluded from this inference, while
  cargo charges/scripts inherit the fitted weapon's weight.
- Non-equipment attribute weights use human-discriminable buckets instead of
  exact-value uniqueness: relative/log buckets for mass, speed, signature, HP,
  recharge, capacitor, cargo, range, scan resolution, PG/CPU/calibration,
  absolute buckets for align/warp, exact buckets for slots/hardpoints/locks,
  quantized profiles for resists and sensor strength. Adjacent scalar buckets
  count as the same human-visible range; this prevents tiny differences from
  producing overweight clues. A small bracket-frequency bonus is applied only to
  the class-varying attributes.
- Standard defense clues use a wider value-matching range than Audit: shield,
  armor and structure HP use a four-times range, while shield recharge and the
  resist layers use twice the base range. This keeps common defensive profiles
  from producing overweight clues.
- Standard never puts bonus clues in its opening or proactive queues; they are
  matching-only. Audit may put bonus clues in its other queue. Bonus clues do not
  narrow the static candidate set by themselves.
- Debrief bonuses are grouped by skill/class with role bonuses in a separate
  group, using SDE text and bold numeric values. Bonus numeric values use the
  fixed light-blue `#c3e9ff` in every mode/theme, not the theme accent. Skill and
  role group headings use the fixed teal `#4c8cb0`. Bonus limited/unique metadata
  participates in weight calculation but is not shown as a visible badge. In the
  dossier traits section, bonus rows have no "Hull bonus X" prefix.
- Ammo inherits the strongest real weapon restriction for weight, but never
  displays a limited/unique/officer/audit marker. Weapon detection uses SDE
  `chargeGroup*` dogma attributes, so utility high slots (Bastion, Command Burst)
  do not contaminate ammo tags.
- Multiple equipment markers are supported: limited, unique, officer (meta 5),
  audit (meta 15), and cargo-only PLEX easter egg. Each marker has a localized
  `title`/`aria-label` hint.
- Audit fallback is always a same-group/same-size representative of the audit
  module itself. It first picks the highest **meta group** present in the same
  slot, then the candidate with the closest **meta level** (attribute 633).
  - Single hierarchy: officer → deadspace → faction → T2 → highMeta → T1.
  - Never use a tier higher than the slot's highest meta group; walk that one
    order from the slot tier downward.
  - Within the first tier that has candidates, pick the closest meta level.
  - Example: X-Type armor hardener meta 16 in low → X-Type repairer meta 16.
  - Example: Entropic Radiation Sink has no deadspace variant → faction Veles
    (meta 8), not officer Zorya.
  - The manifest stores all same-group candidates per tier, not only one.
  - It must never substitute an unrelated module line (e.g. armor repairer into ballistic).
- Before `calculateDogmaFit`, audit fit items are cloned and their type IDs are
  replaced by those tier representatives (cargo untouched). The UI/equipment
  clues keep the original audit IDs; only the attribute calculation is substituted.
- Official SDE de/ru item names are almost entirely English (5,370+ of 5,378);
  this is upstream behavior, not a locale fallback bug. Displaying English there
  matches the EVE client and EVE Ref. Only zh/es/fr/ja/ko have broad SDE names.

## Runtime API caching

- The economy/`ZKILLBOARD` category uses the real target kill value plus cached
  ship-level zKill statistics (90-day losses, usage rank, danger index) when the
  stats request succeeds. No placeholder "data missing" rows are rendered.
- zKill killID responses are cached for 1 hour, keyed by kill ID.
- Ship loss pages, killID responses and ship-level zKill stats are reused for
  1 hour (zKillboard sends `max-age=3600`). The browser relies on its HTTP cache
  for large pages; never use `cache: 'no-store'` for zKillboard or ESI.
- `server/src/zkill.mjs` is the only zKillboard client of the service: User-Agent,
  shared compressed cache, one request per path, two concurrent and spaced
  requests (`ZKILL_MIN_INTERVAL_MS`, default 250), and one global pause for
  `Retry-After`. Only timeouts, 5xx and 429 are retried, once. Arbitration uses it
  through `zkillFetch`.
- `API_CONTACT` is runtime-only configuration: never commit a value, log it or put
  it into the image or manifest. It reaches browsers (and ESI) only with
  `API_CONTACT_PUBLIC=1`, through `/api/v1/meta`. Browser ESI requests identify the
  deployment by its own public origin (`publicSite`), never a configured domain.
- ESI requests go through `esiFetch`: `user_agent` and `compatibility_date` query
  parameters, `Accept-Language: en`, HTTP caching, and a pause when an error or
  rate limit is close or hit. Do not use `/latest/` routes.
- The local zKill cache keeps up to 64 entries so a capped page scan does not
  evict its own pages immediately.
- Failed zKill requests retry up to three times; 429/5xx honor `Retry-After` when
  present.
- Daily failure screens are reason-specific: authoritative time, target service,
  zKillboard, or no eligible killmail. The heading is lore copy; the smaller
  `fatal-code`/body carry the actual error. ESI auxiliary-name failures show a
  non-blocking ESI warning instead of blocking the puzzle. Unspecified failures
  use the generic daily-unavailable screen.
- Safe debug logging goes to the browser console for fatal, zKill, time and ESI
  failures. Public KB/ESI request paths and statuses may be logged. Never log
  client-local state, tokens/nonces, full query URLs, localStorage contents, or
  browser/device information.
- ESI requests append the documented `user_agent` query parameter. Static SDE
  type records use the SDE API and browser caching; character/corporation/alliance
  names have a 6-hour localStorage cache.
- Platinum insurance payouts are read from ESI `/latest/insurance/prices/` and
  cached for about one hour. Use the `Platinum` level's `payout`; never substitute
  the killmail total value or ship base price. Missing data renders `—`.
- The audit fallback simulator uses `data/module-fallback.json` from the build;
  it never calls ESI for module details. zKill browser requests cannot set a
  custom User-Agent or CORS-safe X-User-Agent, so build scripts carry the
  descriptive User-Agent instead.

## Stats and reset

- The profile record comes from the service; practice has no record.
- A run is counted from the first guess, or on starting a Timed run. Free and custom runs never affect stats.
- Streak is measured in consecutive successful days. Any gameplay win counts
  that day once; a missed day or a day with no win resets it.
- Personal progress reset is intentionally unavailable in the current UI; there
  is no reset button or hold gesture. Do not reintroduce it without an explicit
  request.

## Data version

`RULESET_VERSION` + SDE stamp + ship attrs + module count + fallback KB IDs +
usage weights + weighted pool sizes feed `dataVersion`.

- Same SDE + same weights → stable version; no artificial progress reset.
- SDE/weights/pool changes feed `dataVersion`; the unfinished online state is
  keyed by the saved target/killmail, so a same-target rebuild does not reset
  progress. Stats/streak remain a separate localStorage key.
- Bump `RULESET_VERSION` for reveal/rules/scoring changes.

## Known limitations

- SDE builds require network access to `sde.evetech.net`; a complete cached
  `.cache/sde-source` can build offline. The latest release can change more often
  than the old zip, so use `check:sde-cache`/CI `sde-check` rather than rebuilding
  blindly.
- zKill can rate-limit; a ship-page failure aborts target selection instead of
  silently falling back to a static pool or another ship.
- Dogma cannot recover the victim's real skills/mutations; it simulates all-V and
  active modules.
- Cargo/type names absent from local refs use the SDE record API; a network
  failure keeps the numeric fallback and does not block the puzzle.
- The online service is single-instance with SQLite. Rooms are authoritative in
  memory with DB snapshots; there is no horizontal scaling or public leaderboard.
- GitHub Pages publishes only the static/practice build. Online login, scoring and
  rooms require the all-in-one Node service.
