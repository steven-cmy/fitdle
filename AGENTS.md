# FITDLE — Agent & Maintainer Notes

Engineering handoff for people and coding agents. The public introduction and
hosting guide is [README.md](README.md) (English, default) with the Chinese
translation [README.zh-CN.md](README.zh-CN.md).

**Quick orientation**
- Puzzle: guess the victim hull of a real zKillboard killmail from staged clues.
  Gameplays: Standard, Fitting Audit, Timed; Arbitration in rooms only.
- Front end: static ES modules (`index.html`, `js/`, `styles/`), no bundler.
  Back end: `server/` (Node 24, Fastify, WebSocket, `node:sqlite`).
- Build: `prepare:sde` → `build:catalog` → `fetch:usage` → `build:catalog` →
  `build:killpool` → `build`; tests: `npm test` and `npm run test:server` (see *Commands*).
- Rules below are grouped: hard rules first, then architecture, game rules
  (target, KB, reveal), runtime/API, UI copy, and CI/deployment.

## Non-negotiable rules

**Secrecy**
- Never reveal today's target ship, killmail ID, victim name or answer render in
  tests, logs, commits, screenshots or chat. Use non-target/public data in screenshots.
- Never commit `.env`, `.cache/`, `dist/`, `data/`, browser profiles, databases or
  any token. `API_CONTACT` and SSO secrets are runtime-only.

**Versioning and release**
- Every code change gets a **patch** bump (the pre-commit hook does it). Never
  bump `minor`/`major` unless the owner asks. Docs/CI-only commits may skip it
  (`VERSION_BUMP=none` or `--no-verify`).
- Before every commit run `npm test` and `npm run test:server` (run
  `npm install --prefix server` first) and make sure they pass. Before opening a
  release PR also run the full build (`npm run build`) and both suites. If the
  environment cannot run something, say exactly which checks did not run in the
  report so the owner can run them locally; never claim untested work passes.
- Work happens on the local `dev` branch. Ordinary commits may be pushed to
  `github/dev` (no CI runs there). Open/merge PRs into `main`, tag, release,
  publish Pages or images only on an explicit request. Never commit on `main`.
- `CHANGELOG.md` is written (in Chinese) only at a release, which squashes the
  pending local commits into one release commit. See *Release notes*.
- A merge with no program change (documentation or GitHub configuration only)
  needs no new version and no CHANGELOG section. See *Release notes*.
- Nothing published may refer to the AI assistant or tool that helped write it:
  commit messages, branch names, tags, PR titles, bodies and comments, release
  notes, CHANGELOG, README and other files. Add no assistant `Co-Authored-By` or
  session trailers, session links, "Generated with ..." lines or hidden
  attribution comments, even when a tool adds or asks for them by default. This
  applies from now on; do not rewrite history to remove old lines.

**Product scope**
- Keep the puzzle deterministic for every player: fixed online Daily target,
  stable hull/page hashes, completed-month record selection.
- The Node service is the only backend (EVE SSO, targets, stats, rooms). No other
  accounts, second runtime database, public leaderboard, or third-party
  signaling/relay service without an explicit request. zKill/ESI/EVE images and
  the vendored dogma engine are data dependencies, not services.
- Prefer official SDE/zKill/ESI/image sources. Do not cache images in the repo.
- Do not hard-code deployment domains in authored JS/CSS/HTML. Use
  `manifest.links` or the runtime location; share OG images use `PUBLIC_ORIGIN`
  (CI fallback `PAGES_URL`, then GitLab's `CI_PAGES_URL`).

**UI and copy**
- Follow EVE Photon UI: dark compact panels, fine borders, clear hierarchy. Do not
  add effects or decoration that were not requested; remove rather than add.
- Interface strings live in `js/messages/<locale>.js`, one flat file per language
  with identical keys. Terms and sources are in `docs/i18n-glossary.md`.
- Localization priority: official EVE localization, then community wording, then
  own translation. Never translate EVE terms/names/official strings; record
  ambiguous terms in the glossary.
- The README exists in two languages: `README.md` (English, default) and
  `README.zh-CN.md` (Chinese). Every README change updates both in the same
  commit, with the same sections, links and image. Both keep the
  `English | 简体中文` switch at the top.

## Architecture

- Static ES modules in `js/`, `styles/`, `index.html`, assembled into `dist/`
  by `scripts/build-dist.mjs`; no bundler.
- A lightweight Node service in `server/` provides EVE SSO sessions, online
  Daily/random targets, run/stat recording, and authoritative WebSocket rooms.
  It can serve `dist/` and `/api`/`/ws` from one origin.
- Online Daily is server-pinned once per game day and cached in SQLite. Online
  Standard/Audit/Timed get a server-issued random target per run; practice gets
  a client random/explicit KB target and never scores.
- `data/manifest.json` is generated by `scripts/build-catalog.mjs`; it contains
  pools, links, data version, SDE release/build, zKill snapshot, version and
  optional `apiBase` (only when `API_ORIGIN` differs from `PUBLIC_ORIGIN`).
- `data/catalog.json`, `data/refs/*.json`, `data/killpool.json` are generated.
- `dist/` contains authored `js/`, `styles/`, `assets/`, generated `data/`, and
  `vendor/dogma-engine/`.
- Build-time configuration lives in ignored `.env` (see `.env.example`), with
  environment variables taking precedence. The Node service loads the same root
  `.env`; `PUBLIC_ORIGIN` / optional `API_ORIGIN` derive callback, CORS, cookie
  security and share URLs.

### Online service and multiplayer

- `index.html` is the only app entry. `js/main.js` boots the puzzle; `js/api.js`
  talks to the same-origin service; `js/rooms.js` embeds the room view into the
  main shell and hands Arbitration to the single-player hero/dossier.
- `server/` is Node 24 + Fastify + `@fastify/websocket` + `@fastify/cookie` +
  `@fastify/static` + `jose` + built-in `node:sqlite`. It serves `dist/`, `/api`
  and `/ws`; a split deployment sets `API_ORIGIN` and derives CORS/callback.
- EVE SSO is authorization-code + PKCE, state/JWKS validation, minimal
  `publicData` scope. Only the `name` and character-id (`sub`) claims are used.
  Accounts are keyed by
  normalized character name; alts are separate; character rename creates a new
  account. The character ID is stored only to render the official EVE portrait;
  no corporation, alliance, avatar image or other identity data is stored.
  The token endpoint is read from the SSO metadata document; the client secret stays
  server-side and the callback is `${API_ORIGIN || PUBLIC_ORIGIN}/api/v1/auth/eve/callback`.
- Modes are determined by auth/back-end availability: guest or service failure is
  Practice; logged-in is Online. Mode is not a manual toggle. Practice provides
  Standard/Audit/Timed, random or explicit KB, no scoring. Daily is online-only.
- Online Daily is pinned once per game day and cached in SQLite. Online
  Standard/Audit/Timed get a server-issued random target per run. A current KB
  entered from a share link becomes an online custom run when logged in; custom
  runs can be played and resumed but never enter streaks, win days or difficulty counters.
- The service records solo guesses: `POST /online/runs/:id/guess {shipId}` counts,
  deduplicates and judges them; `finish` only accepts a Timed loss. A run counts
  from its first guess, a Timed run from starting the clock (`begin`). `start` returns the player's open run of that gameplay, so a
  reload, a closed page or another device continues it. `abandon` (NEW TARGET, after
  a confirmation) loses a started run and forgets an unstarted one; a started run
  unfinished for 24 hours is lost. NEW TARGET is disabled while a random Timed target
  waits for its clock: it shows no clue yet. Explicit `kb` targets can be left.
- `js/run-sync.js` delivers solo guesses in order, keeps unsent ones in
  `fitdle:v1:pending-runs` and retries; resending is harmless.
- **The answer stays on the service until the run ends** (online Daily, random
  Standard/Audit/Timed and race rooms; not Arbitration, explicit KB runs or
  Practice). `server/src/puzzle.mjs` builds the puzzle once at the start (clue set,
  reveal plan, a snapshot of the live zKill statistics, Audit/Timed dogma) and
  stores it in `online_runs.puzzle_json`; rooms keep it in memory per round. A
  player only ever receives `board`: every open-board clue as `{i,k,c,w,hidden}`
  until released, released clues in full, sealed clues (equipment, cargo, bonus)
  only once released and in release order, `sealed` = categories still holding
  hidden sealed clues, `feedback` = the match of each guess, `caseId` = an opaque
  file number. `target`, killmail, kill id, `sampleKill` and `fittedKills` come
  only after the end (`endReason`: solved, attempts, gave-up, abandoned, expired,
  exhausted). Released clues stay released. Timed releases follow the service
  clock (`TIMED_RELEASE_MS`, 30 s); the page polls after each release and the
  service ends a Timed run with nothing left to release. Puzzles of runs ended
  more than two days ago are pruned; an older run gets its puzzle on the next
  visit. The page holds no answer: no local target cache, no zKill or dogma
  lookups with the answer hull, nothing in localStorage. A guess is one round
  trip; the page shows it as pending and accepts no next guess until the service
  answered (no offline queueing of several guesses).
- Run protocol: `/api/v1/online/*` requests carry `x-fitdle-run-protocol`
  (`RUN_PROTOCOL_VERSION` in `js/run-sync.js`); another value gets 426
  `client-outdated` and the page shows the reload screen. The room socket names
  `PROTOCOL_VERSION` (`js/mp/protocol.js`) as `?v=`; another value gets an
  `error client-outdated` message and close 1008 `client-outdated`. Bump the
  matching version whenever the run or room messages change shape.
- Room guesses go through `raceGuess {roundId, shipId}`; the server counts, judges
  and keeps the Timed cooldown, and answers the player with `raceGuesses`
  (guesses, status and that player's `board`; `target` once their part or the
  round is decided). `endlessPrepare` carries neither target nor clues;
  `endlessStart` carries each player's opening board; `raceBoard {roundId}` asks
  for the board the Timed clock has reached and ends a part with nothing left to
  release (`endReason: exhausted`). `raceResult` only reports a Timed give-up.
  Leaving for good (or the grace ending) during a running round is a loss of that
  round; being kicked is not.
- Clients submit full hull names or ship ids. `js/ship-query.js` resolves
  abbreviations and partial names and asks when several hulls fit; the server never
  accepts abbreviations.
- The room state API answers players of the room only. Scores reset only between
  matches. Seated players rejoin without the password; empty passwords are no guess.
- Requests are limited per player (`server/src/limits.mjs`). Logs carry paths without
  query strings, startup logs a few lines (`server/src/startup.mjs`): release, API, run and WebSocket protocol
  versions, origin, data, sign-in flags, target and limit settings; yes/no for secrets, never values, and the SSO state is bound to the browser by a short-lived cookie.
- `FITDLE_DEV_AUTH` is ignored in production unless `PUBLIC_ORIGIN` is loopback.
- zKillboard killmails lose `attackers` on arrival (`js/killmail.js`); nothing uses it.
- `multiplayer` is a separate room surface behind login. A room has no default
  gameplay/rule; the owner selects Standard/Fitting Audit/Timed (same-file race) or
  Arbitration and settings before a match and again between
  matches. Players are retained; scores are room-cumulative and the owner can
  reset them. Daily cannot be selected in a room.
- Arbitration is dealer-rotation: six small rounds per dealer stint, no timer. An Arbitration
  room can run 1..N **big rounds**, where one big round is one pass through the
  active dealer order. The small-round rules are fixed; only the big-round count
  is host-configurable. The dealer publishes at least one unpublished clue per
  round (or all), and at least one with weight while any weighted clue is still
  selectable (`clue-weight-required`); active players guess once. If every clue
  is published, players keep guessing each round. The stint ends after six
  rounds or when every player still in the room has solved.
- Arbitration scoring lives in `js/mp/rules.js` (`ARBITRATION_SCORING`, shared by
  server and dossier preview). f = published share of the total clue weight
  after the dealer publishes; n = players at stint start (fixed). A solve in
  round k pays `solveBase*(1-f)+solveEarly*(7-k)` at once. After each round
  every unsolved player gives the dealer `dealerRound*f`; when the stint ends
  (six rounds, all solved, dealer leaves or host ends) the dealer gets
  `dealerEnd*n*f`. The dealer total is the raw sum / n, credited with cumulative
  rounding (`arbitrationDealerCredit`). A player who leaves stays unsolved to the
  end of the stint and keeps earned points; a solved leaver stays solved. Leaving
  dealer / host end settle the current round and the end bonus before
  `matchResult`. When the scheduled dealer is gone, the next connected pilot in
  the big-round order deals. Scores are room-only, never stored on accounts.
  Clues on the wire carry `p` (share of total weight), never per-player values.
  `arbitration_rounds` stores `published_share` and `unsolved` per round for
  later coefficient tuning.
- Room state, target selection, clue release, guessing, scoring and timers are
  authoritative on the server. Clients never send scores. The server keeps
  anonymous difficulty counters (see Difficulty counters) and per-round arbitration
  rows for later tuning; no leaderboard UI/API yet.
- `ROOM_MAX_PLAYERS` controls total room seats (default 8, allowed 2..32,
  including spectators/offline seats). Existing names rejoin without consuming
  a new seat.
- `ROOM_ARBITRATION_BIG_ROUNDS` / `ROOM_ARBITRATION_MAX_BIG_ROUNDS` define the Arbitration default and
  host limit for big rounds. `ROOM_TIMED_DURATION_MINUTES` /
  `ROOM_TIMED_MAX_DURATION_MINUTES` do the same for Timed room duration.
- `ROOM_RECONNECT_GRACE_MS` (default 60000, range 5000..300000) keeps a
  disconnected player in the room and the current owner in place until the grace
  ends. Reconnecting restores the same player; only after the grace may the
  player be removed, the owner transferred, or a disconnected Arbitration dealer
  end the match. Explicit leave and host kick are immediate. The Local list shows
  a spinner and `room.reconnecting` while a player is inside the grace.
- Chat is ephemeral, sanitized, length-limited and rate-limited; it is not
  persisted. Chat sends carry a client id, and the server acknowledges success or
  returns a localized rate/validation error. The client keeps the draft until an
  acknowledgement.
- The service owns WebSocket delivery. There is no PeerJS/WebRTC/TURN, no host
  tab dependency, and no iframe race. Session cookie auth is used for WS.
- Room connections: the server pings every 25 s and drops a socket after missed
  answers; the client sends an application `ping` every 25 s, reconnects at once
  after a drop and then backs off. A newer connection of the same player closes
  the older one (4001). Closed sockets are logged without names, chat or targets.
- Asynchronous target loads go through `loadMatch`; check `current()` before
  touching the room. Only one load runs per room, and ending the match cancels it.
- The owner is always a player in the room (`ensureOwner`). Players who never
  connect leave after the reconnect grace. Arbitration progress after a leave,
  timeout or dealer return goes through `checkArbitrationProgress`.
- Room messages and wrong room passwords are limited per player.
- `js/rooms.js` panels are skeletons of regions; update regions, never replace a
  panel. The chat input, open selects and running holds must survive updates.
- A round result is kept until the server confirms it and is resent on reconnect.
- Room chat is presented as the Subspace Communication Beacon. Use the exact
  English name/source string and localized equivalents in `js/i18n.js`.
- When the room socket is not connected, show the localized
  `room.chatUnavailable` system line and keep the chat input disabled.
- The Daily reset CTA is enabled only after the local countdown has crossed into
  a new game day; clicking it reloads into the new Daily target.

### Difficulty counters

Two SQLite tables hold anonymous counters of how hard each target is; nothing
in them says who or which room played, and no per-play row is written. They are
written by `recordPlay` / `recordPlays` in `server/src/stats.mjs` and are not
used for target selection.

- `kill_difficulty(kill_id, gameplay, ship_id, won, lost, abandoned,
  won_guesses_sum, won_ms_sum, first_at, last_at)`, one row per killmail and
  gameplay. Rows whose `last_at` is older than `FITDLE_STATS_KILL_RETENTION_DAYS`
  (default 60) are deleted by the 10-minute cleanup, so the table stays bounded
  (about one row per distinct killmail played in the last 60 days; roughly 100
  bytes each, so even 1000 daily players at 10 plays each stay near 60 MB of row
  data; with the primary key and the `last_at` index the worst case is about
  100-150 MB. That is the upper bound where every play is a different killmail).
  `first_at` and `last_at` are rounded down to the UTC day, so a row cannot be
  matched to an exact time in other logs.
- `ship_difficulty(ship_id, gameplay, ...same counters..., updated_at)`, one row
  per hull and gameplay, kept for good (a few hundred rows).
- `gameplay` is `daily`, `standard`, `audit`, `timed` or `arbitration`. Solo
  random runs and race rounds share the standard/audit/timed rows; the Daily has
  its own. Custom killmails and offline/practice play are never recorded.
- Outcomes: `won`; `lost` (six misses, a timed give-up, a race round timing out);
  `abandoned` (the player took another target, the run expired after a day, or
  they left the race room mid-round). A play counts from the first guess (timed:
  from starting the clock); a race leaver with no guess is not counted at all.
  Win rate is `won / (won + lost)`; abandoned plays are kept out of it and
  reported separately.
- `won_guesses_sum` adds the guesses of won plays only; `won_ms_sum` adds the
  time of won plays in timed gameplay only (other gameplays measure no time).
- Arbitration is recorded once per stint when at least one guess was made:
  every player who started the stint counts, solvers as `won`, everyone else
  (leavers included) as `lost`. It has no guess or time sums, and it is a
  separate gameplay because the dealer chooses which clues are published, so it
  measures the dealer as much as the target. Do not mix it with the others when
  choosing targets. A race round that ends before it is settled records nothing
  for that round, including players who had already won or lost in it: the host
  ending the session, the last player leaving, or the room being closed. Rooms
  are not restored after a restart, so a round running at that moment is never
  recorded either. The single-player UPDATE and its counter write are not one
  transaction, so a crash between the two loses that one play.
- Writing statistics is best effort. A failing write (full disk, locked
  database) is caught inside `stats.mjs`, logged as one warning without any id,
  and the play is lost; it never stops a run, a round or a timer.
- The older `target_exposures` and `target_stats` tables are no longer written;
  databases that have them keep them untouched.
- Reading: `npm run stats:difficulty -- --by ship|kill --gameplay all|daily|
  standard|audit|timed|arbitration --min 5 --limit 30 [--easiest] [--json]`
  (`docker exec <container> node server/src/difficulty-report.mjs ...` on the
  deployment). It opens the database read-only, lists rows with at least `--min`
  won-or-lost plays, hardest first, and `all` sums the four player gameplays.
  Averages only use plays that record the value: guesses skip arbitration, time
  counts timed wins only (so `all` shows the timed average). Unknown options,
  options without a value and `--k=v` mistakes are errors.
  `difficultyReport(db, options)` in `server/src/difficulty-report.mjs` is the
  same query for code. There is no public API or UI.

## Data flow

1. `prepare:sde` calls the official SDE HTTP API (`sde.evetech.net/tranquility/latest/`),
   downloads the release-specific JSONL tables whose version changed into
   `.cache/sde-source/`, reuses the rest, and normalizes them.
2. `build:killpool` builds a small offline fallback pool from zKill global losses
   and stores zKill's server `Date` as `serverDate`.
3. `fetch:usage` downloads the monthly ship usage file of the `data` branch to
   `.cache/ship-usage.json` (see *Usage data*). Builds make no per-hull zKill
   requests. Economy clues use the live ship statistics: `losses90`, recent kill
   rank (`shipsDestroyed`) and a recent kill/(kill+loss) danger index from
   zKill's 90-day `rankings.recent` bucket. The block title, not each row, says
   90 days.
4. `build` reads normalized SDE + usage file + killpool and writes `data/` and
   `dist/`. It also emits a compact `data/module-fallback.json` from
   `typeDogma` for the six attributes used by the audit fallback simulator, so
   that fallback never calls ESI at runtime.
5. Online runtime: the service reads the server game day, resolves a Daily target
   once (HMAC server seed, build-time pools, zKill loss pages), caches the
   killmail, and serves it to logged-in clients. Online Standard/Audit/Timed get
   a server random target per run. Practice uses client random/explicit KB only.
   No local clock or static target is used for online Daily.

## Target selection

One server-side picker (`server/src/targets.mjs`, pure rules in
`server/src/selection.mjs`) serves the Daily, online Standard/Audit/Timed, race
rooms and arbitration rooms. Practice (static build, browser) still uses its own
client-side random pick from the manifest pools (`normalShipPool` etc.) and never
scores. `scripts/build-catalog.mjs` builds those pools with
`scripts/practice-pools.mjs` from `.cache/ship-usage.json`: usage over the last
3 complete months before the file was made, Standard favouring used hulls and
Audit the others, with the default group factors; a hull whose months hold no
loss is left out. Without usable data the build warns, gives every hull weight 1
and goes on.

### Hull queue

- Every SDE hull in the catalog starts at weight 1. Its zKill kills as an
  attacker (`shipsDestroyed`) over the last `FITDLE_USAGE_WINDOW_MONTHS` (3)
  complete calendar months add a bonus on a log scale, capped so that the heaviest
  ordinary hull is at most `FITDLE_USAGE_MAX_RATIO` (3) times the lightest. A hull
  with no usage keeps exactly 1; there is no extra floor.
- Then each hull is multiplied by its group factor,
  `FITDLE_SHIP_GROUP_FACTORS` (default `29:0.2,31:0.3,237:0.5`: capsules, shuttles,
  rookie ships; group ids confirmed against the SDE catalog: 2, 11 and 9 hulls).
  Factor 0 removes the group. Hulls of a factored group do not set the scale of
  the usage bonus.
- Weights are computed per UTC day from `data/ship-usage.json` (see below) and
  turned into a weighted order without replacement (exponential keys: heavier
  hulls tend to come first, every hull appears once). The same seed always gives the
  same order. Daily: seed = HMAC(server secret, gameDay, algorithmVersion); random
  picks: a fresh random seed.
- The picker walks the queue from the top (at most 12 hulls, 25 s per pick). A
  hull without a usable killmail (for example tournament hulls) is remembered for
  `FITDLE_NO_KILL_RETRY_HOURS` (24) per empty-hull setting and the next hull is
  tried. A refusal caused only by a room's own history is not remembered.
  A zKill error aborts the pick; there is never a static or other-day fallback.
- `algorithmVersion` is `online-v2`. `dataVersion` is never part of the Daily seed.

### Killmail of a hull

- The target is a loss: `/api/losses/shipTypeID/{id}/year/{Y}/month/{M}/page/{N}/`
  (month without zero padding, 200 per page, pages 1..100, newest first, empty
  page past the end, 1 hour cache; `startTime`/`endTime` are disabled upstream and
  are not used).
- The month is drawn by time weight among months that have losses, from
  `FITDLE_KB_SELECTION_START_DATE` to the end of the last complete month
  (half-life `FITDLE_KB_RECENCY_HALF_LIFE_DAYS`, 365; older months count less but
  never zero). The page is uniform over `ceil(losses / 200)` pages of that month
  (capped at 100); an empty overshoot page falls back to page 1. One eligible
  killmail of the page is drawn uniformly. At most 3 requests per hull.
- Eligible: victim hull matches, date inside the period, fitted when empty hulls
  are off, not already played in that room. Page killmails are complete, so no
  `killID` request is needed.
- A hull the usage file cannot size (no entry because it is new in the SDE, or an
  entry with no month) reads the first page of one of the last 12 complete
  months, drawn by the same time weight, up to 3 requests. The newest unfiltered
  page is never used: for a busy hull it is all this month, which is not eligible.

### Usage data

- `data/ship-usage.json`: per hull `{ at, m: { YYYYMM: [shipsDestroyed, shipsLost] } }`
  from the single-hull zKill statistics (`/api/stats/shipTypeID/{id}/kills/`, the
  path of the API catalog; without `/kills/` it redirects). `shipsDestroyed` is the
  usage measure, `shipsLost` sizes the pages of a month. **The `months` field is
  not documented by zKillboard**: it was found in real answers. The parser treats
  a missing or odd field as "no data" instead of failing; the script refuses to
  write when fewer than half of the answers have months, so if upstream drops the
  field the workflow fails, the old file stays, and the data slowly ages (the
  server warns at start). Only complete calendar months are kept: the script drops
  the month it runs in, and the server drops, when it reads a file, every month
  not yet over at the time that entry was fetched.
- The workflow `.github/workflows/usage.yml` runs on the 2nd of every month (and
  manually, optionally only for hulls missing in the file), runs
  `scripts/build-ship-usage.mjs` (about 430 requests, one at a time, 1 s apart,
  generic User-Agent with the repository URL only, Retry-After honoured, previous
  entries kept for failed hulls, refuses to write if the format looks wrong, and a
  401/403 stops the whole run at once without writing) and
  commits the result straight to the `data` branch (`ship-usage.json`). Main is not
  touched and no pull request is involved; the workflow needs `contents: write`.
  The server warns at start when the file is older than `FITDLE_USAGE_STALE_DAYS`
  (45: one monthly cycle plus buffer; keep it in line with the workflow's cron).
- The main CI downloads that file (`npm run fetch:usage`, never fails the build)
  into `.cache/ship-usage.json`; the runtime stage of the Docker image copies
  that file (or an empty placeholder) to `data/ship-usage.json`. It must not be
  put into the build stage's `data/`, which `npm run build` deletes and
  recreates. The server reads it at start (`FITDLE_SHIP_USAGE_FILE` overrides the
  path).
- Fresh data without a new image: `server/src/usage-refresh.mjs` loads a cached
  copy (`ship-usage.cache.json` next to the database) at start when it is newer
  than the image's file, then asks the data branch for the file at start and every
  `FITDLE_USAGE_REFRESH_HOURS` (168; empty or 0 turns the refresh off). The
  address is `FITDLE_USAGE_URL` (default: the raw `ship-usage.json` of this
  repository's `data` branch). One request, generic User-Agent without personal
  details, `If-None-Match` with the last ETag, 15 s timeout, no retry storm (after
  a failure the next try is 6 h later at the earliest). The file is adopted only
  if it parses, has the expected shape, a generation date and is newer than what
  is loaded; then it is cached. Any failure keeps the data in use. The startup
  log names the source (image, cache or remote) and its age; a remote refresh
  after start is logged when it changes something.

### Shelf and rooms

- Random targets come from a shelf of prepared targets in the `target_shelf`
  table (`TARGET_SHELF_SIZE` 150, 0 turns it off; `TARGET_SHELF_TTL_HOURS` 24). Each
  row is handed out once and carries a has-fit flag, so a switched-off empty-hull
  pick skips empty ones. Below half full a background refill runs, paced by one
  shared gate (`TARGET_REFILL_INTERVAL_MS`, 2000 = 0.5 requests a second) so live
  picks keep their share; it starts only after a successful pick, skips killmails
  already on the shelf, and an empty shelf means a pick is made at once. The Daily
  never uses the shelf (it is seeded and pinned in `daily_pins`).
- Rooms play a killmail once per room (`room.usedKillIds`); the same hull may come
  again, and rooms ignore each other. Arbitration takes its target from the same
  picker (`roomTarget`) and `buildDealerRound` in `js/mp/target.js` only builds the
  clues. The old preference of arbitration for fitted hulls is gone: the room's
  empty-hull setting alone decides.
- The empty-hull rules are unchanged: personal setting for online single play
  (`allowEmpty` sent to `/online/start`), host setting for rooms, deployer setting
  `FITDLE_DAILY_ALLOW_EMPTY` for the Daily (a pinned day keeps its target).
  Explicit `kb` targets ignore all of it.
- Reveal seeds may still contain the date; clue statistics need not be unified.

## KB selection

- The game day boundary is `FITDLE_GAME_DAY_START_UTC` (`HH:MM` UTC or minutes
  0-1439; default `11:00`). The build writes it into the manifest; the server
  reads it at startup and publishes it in `/api/v1/meta`; the container
  entrypoint (`render-runtime-origin.mjs`) writes it into `dist/data/manifest.json`
  and its .br/.gz copies; the page prefers the meta value. So a runtime change
  needs no rebuild. Invalid values are logged and fall back to the build value.
- The static build has no Daily (offline turns it into a Standard run). Its
  Practice uses the older client-side random pick and respects the personal
  `allowEmptyKb` setting.
- `FITDLE_KB_SELECTION_START_DATE` is a global lower bound for all modes.
  Explicit `?kb=` links bypass it.
- Service targets use the complete killmail from the loss page; the browser uses
  the killmail the service sent. Ship loss pages and killID responses are reused for
  the hour zKillboard allows. Failures are not cached.
- A network/API failure aborts selection. Never use the static kill pool, an
  SDE-only dossier, the local clock, another day or another ship as a fallback.
- If every queued ship has no candidate, show the localized NO TARGET screen with
  Free mode. Free random targets respect the KB lower bound; explicit `kb` links
  do not.
- There is no archive mode; historical-day consistency is intentionally not
  supported. Only the current game day is synchronized.

## Reveal rules

- Every answer builds one immutable `revealPlan` at `buildAnswerData()` time:
  opening queue plus per-category queues. Queue order is a weighted random
  permutation (low weights more likely early, never a strict weight sort).
- Queue seeds use the server target seed for Online and the stable KB seed for
  Practice, then add mode, timed/standard and queue name. Guesses are never part
  of a seed.
- Opening: budget 9, max weight 13, min 3 / max 7 clues, candidate floor 6; no
  cargo and no bonus in Standard opening, no tagged equipment, one identity and
  one equipment.
- Standard only: guesses reveal shared static values. Bonus clues are never
  proactively revealed; they match only on the same `termKey`
  (`section|normalizeBonusKey(text.en)`), regardless of numeric value/unit. All
  target bonuses sharing that term are revealed.
- Standard misses: equipment queue consumes its weight budget
  (`base + floor(equipmentCount / divisor)`, capped); cargo queue consumes its own
  independent weight budget. Guessed/already-revealed clues skip without cost.
- Audit: no guess matching. Equipment queue gets `miss` per miss; other queue gets
  `1 + ceil(shortfall / 2)`; cargo gets `max(1, ceil(cargoCount / divisor))`.
  Equipment shortfall transfers to the other queue; cargo/other exhaustion does
  not invent new transfers.
- Timed: one mixed queue, no guess matching; each release consumes the original
  `1, 1, 2, 2, 3, 3...` quota. Opening uses the same opening queue.
- Reveal growth must be monotonic: later rounds only append; a previously shown
  clue never disappears.
- All fitted modules are simulated as online and active, never overheated; cargo,
  fuel and spare fighter-bay modules stay offline. Audit simulation keeps only
  one propulsion module (larger size first, then Microwarpdrive over
  Afterburner) and simulates cloaking devices online but inactive.
- Audit static weights start from base stats (so fitted values do not inflate
  weight), then a clue whose fitted value differs from the **all-V no-modules
  baseline** is multiplied by 0.7. Skill-only changes do not reduce weight; only
  module effects do. `calculateDogmaBaseline` supplies that baseline.
- Equipment parsing keys by `module type + slot`; a battery fitted in mid and also
  carried in cargo must render as two lines with their own quantities.
- Fighter tubes (158..161) are `fighter`; flag 155 is `fighterBay` and flag 133 is
  `fuelBay`. Only category-87 fighters stay in fighter slots; spare modules,
  charges and scripts there are cargo.
- Standard mode always includes structure resists in the opening clues and gives
  them weight 0 because every hull has the same base structure resists.
- Audit resistance clues follow the fitted resist gear, not only the base hull
  profile. No resist gear, or only a plain/T1/T2 damage control, caps the clue
  low because calculated values are shared; faction+ damage controls and any
  resistance module floor the clue to at least that module's weight; Assault
  Damage Controls raise it sharply (structure at least 9.5, shield/armor at
  least 8.8); non-uniform structure resists (audit weather) reach 9.8.
- Faction+ damage controls and resistance modules receive an 8.2 equipment
  weight floor; their resistance clue cannot weigh less than the module.
- Sensor strength is one clue. It displays only the sensor type(s) with a
  non-zero value: normally one, in the owning race's colour; two special shuttles
  have all four equal. Shield recharge time is a static SDE clue. In Audit their
  fitted values come from the dogma engine; shield recharge is stored/displayed
  in seconds. Drone bay/bandwidth zero always renders as `0`, not a “No drone
  bay” label.
- Low-slot weapon upgrades are weighted by the weapon family they improve
  (projectile/energy/hybrid/missile/drone/disintegrator/turret); matching fitted
  weapons raise weight from 5.8 to at least 7.4.
- Limited modules get a scarcity bonus from how many catalog hulls their
  `fitRestrictions` cover: fewer compatible hulls = higher weight.
- All fitted modules on Corvettes (group 237) and Zephyr (group 1022) are treated
  as limited and weighted accordingly, because those hulls carry built-in gear.
- Fighters are `limited` and weigh 10; Excavator/Pluto/special mining drones are
  `unique` and weigh 10. Jump fuel weighs 10.
- Rigs weigh at least 8.5; large/capital rigs reach 10.
- All equipment weights are clamped to 1..10, matching the x/10 UI.
- Equipment size adds weight: Capital/XL +7, Large +2.2, Medium +0.8.
- Ship bonuses use structured SDE entries: section (role/types), skill type ID,
  importance, numeric bonus, unit ID, localized text, canonical term key, and
  exact term+value key. Never identify a bonus by array index or `importance`
  alone. Rebuild these keys from raw SDE whenever the SDE changes.
- Bonus term identity is section + normalized English text. Exact-value identity
  adds the numeric bonus and unit. More ships sharing a term lowers weight; if
  the value is shared too, lower it further. Distinct values add weight by their
  normalized spread. A unique term is weight 10 and tagged `unique` like
  equipment. Role bonuses are always `limited`; skill bonuses that target a
  race/class are also `limited`. All `limited` bonuses get a weight increase,
  and role bonuses have a higher floor.
- Equipment restriction markers describe the SDE restriction shape, not hull
  count: one `shipGroups` entry or one `shipTypes` entry → `unique`; multiple
  groups/types → `limited`; no restriction → no marker. A unique equipment clue
  weighs 10; limited clues use breadth scarcity.
- Bonus `showinfo` module links carry `links` IDs into the catalog. A bonus
  inherits its linked equipment's marker: one restriction group/type makes the
  bonus `unique` and weight 10, multiple groups/types make it `limited`, and
  unrestricted equipment contributes no equipment-derived marker. Limited
  equipment and its bonus use the same breadth-based rarity weight, so rarer
  restrictions raise both. Assault Damage Control has two groups and is limited;
  Bastion modules have one Marauder group and are unique. Mining-laser/Strip
  Miner bonuses use the same range rule.
- Module metadata includes `requiredSkills`. A bonus linked to a skill affects
  every fitted module whose required skills include it; a bonus linked to a
  module affects that module and its module group. Affected fitted equipment and
  cargo clues are raised to at least the bonus weight, and high-slot/cargo
  ammunition then inherits the boosted weapon weight.
- Module metadata includes `power`/`cpu` and ships include `rigSize`. A fitted
  module's base PG/CPU requirement infers the smallest hull bracket where at
  least half the ships can fit it; medium/large/capital fits receive a size-based
  weight floor. Cargo spare modules are excluded from this inference, while
  cargo charges/scripts inherit the fitted weapon's weight.
- Non-equipment attribute weights use human-discriminable buckets instead of
  exact-value uniqueness: relative/log buckets for mass, speed, signature, HP,
  recharge, capacitor, cargo, range, scan resolution, PG/CPU/calibration,
  absolute buckets for align/warp, exact buckets for slots/hardpoints/locks,
  quantized profiles for resists and sensor strength. Adjacent scalar buckets
  count as the same human-visible range; this prevents tiny differences from
  producing overweight clues. A small bracket-frequency bonus is applied only to
  the class-varying attributes.
- Standard defense clues use a wider value-matching range than Audit: shield,
  armor and structure HP use a four-times range, while shield recharge and the
  resist layers use twice the base range. This keeps common defensive profiles
  from producing overweight clues.
- Standard never puts bonus clues in its opening or proactive queues; they are
  matching-only. Audit may put bonus clues in its other queue. Bonus clues do not
  narrow the static candidate set by themselves.
- Debrief bonuses are grouped by skill/class with role bonuses in a separate
  group, using SDE text and bold numeric values. Bonus numeric values use the
  fixed light-blue `#c3e9ff` in every mode/theme, not the theme accent. Skill and
  role group headings use the fixed teal `#4c8cb0`. Bonus limited/unique metadata
  participates in weight calculation but is not shown as a visible badge. In the
  dossier traits section, bonus rows have no "Hull bonus X" prefix.
- Ammo inherits the strongest real weapon restriction for weight, but never
  displays a limited/unique/officer/audit marker. Weapon detection uses SDE
  `chargeGroup*` dogma attributes, so utility high slots (Bastion, Command Burst)
  do not contaminate ammo tags.
- Multiple equipment markers are supported: limited, unique, officer (meta 5),
  audit (meta 15), and cargo-only PLEX easter egg. Each marker has a localized
  `title`/`aria-label` hint.
- Audit fallback is always a same-group/same-size representative of the audit
  module itself. It first picks the highest **meta group** present in the same
  slot, then the candidate with the closest **meta level** (attribute 633).
  - Single hierarchy: officer → deadspace → faction → T2 → highMeta → T1.
  - Never use a tier higher than the slot's highest meta group; walk that one
    order from the slot tier downward.
  - Within the first tier that has candidates, pick the closest meta level.
  - Example: X-Type armor hardener meta 16 in low → X-Type repairer meta 16.
  - Example: Entropic Radiation Sink has no deadspace variant → faction Veles
    (meta 8), not officer Zorya.
  - The manifest stores all same-group candidates per tier, not only one.
  - It must never substitute an unrelated module line (e.g. armor repairer into ballistic).
- Before `calculateDogmaFit`, audit fit items are cloned and their type IDs are
  replaced by those tier representatives (cargo untouched). The UI/equipment
  clues keep the original audit IDs; only the attribute calculation is substituted.
- Official SDE de/ru item names are almost entirely English (5,370+ of 5,378);
  this is upstream behavior, not a locale fallback bug. Displaying English there
  matches the EVE client and EVE Ref. Only zh/es/fr/ja/ko have broad SDE names.

## Runtime API caching

- The economy/`ZKILLBOARD` category uses the real target kill value plus cached
  ship-level zKill statistics (90-day losses, usage rank, danger index) when the
  stats request succeeds. No placeholder "data missing" rows are rendered.
- zKill killID responses are cached for 1 hour, keyed by kill ID.
- Ship loss pages, killID responses and ship-level zKill stats are reused for
  1 hour (zKillboard sends `max-age=3600`). The browser relies on its HTTP cache
  for large pages; never use `cache: 'no-store'` for zKillboard or ESI.
- `server/src/zkill.mjs` is the only zKillboard client of the service: User-Agent,
  shared compressed cache, one request per path, two concurrent and spaced
  requests (`ZKILL_MIN_INTERVAL_MS`, default 250), and one global pause for
  `Retry-After`. Only timeouts, 5xx and 429 are retried, once. Every service
  target, arbitration included, goes through it.
- `API_CONTACT` is runtime-only configuration: never commit a value, log it or put
  it into the image or manifest. It reaches browsers (and ESI) only with
  `API_CONTACT_PUBLIC=1`, through `/api/v1/meta`. Browser ESI requests identify the
  deployment by its own public origin (`publicSite`), never a configured domain.
- ESI requests go through `esiFetch`: `user_agent` and `compatibility_date` query
  parameters, `Accept-Language: en`, HTTP caching, and a pause when an error or
  rate limit is close or hit. Do not use `/latest/` routes.
- The local zKill cache keeps up to 64 entries so a capped page scan does not
  evict its own pages immediately.
- Failed zKill requests retry up to three times; 429/5xx honor `Retry-After` when
  present.
- Daily failure screens are reason-specific: authoritative time, target service,
  zKillboard, or no eligible killmail. The heading is lore copy; the smaller
  `fatal-code`/body carry the actual error. ESI auxiliary-name failures show a
  non-blocking ESI warning instead of blocking the puzzle. Unspecified failures
  use the generic daily-unavailable screen.
- Safe debug logging goes to the browser console for fatal, zKill, time and ESI
  failures. Public KB/ESI request paths and statuses may be logged. Never log
  client-local state, tokens/nonces, full query URLs, localStorage contents, or
  browser/device information.
- ESI requests append the documented `user_agent` query parameter. Static SDE
  type records use the SDE API and browser caching; character/corporation/alliance
  names have a 6-hour localStorage cache.
- Platinum insurance payouts are read from ESI `/latest/insurance/prices/` and
  cached for about one hour. Use the `Platinum` level's `payout`; never substitute
  the killmail total value or ship base price. Missing data renders `—`.
- The audit fallback simulator uses `data/module-fallback.json` from the build;
  it never calls ESI for module details. zKill browser requests cannot set a
  custom User-Agent or CORS-safe X-User-Agent, so build scripts carry the
  descriptive User-Agent instead.

## Stats and reset

- The profile record comes from the service; practice has no record.
- A run is counted from the first guess, or on starting a Timed run. Free and custom runs never affect stats.
- Streak is measured in consecutive successful days. Any gameplay win counts
  that day once; a missed day or a day with no win resets it.
- Personal progress reset is intentionally unavailable in the current UI; there
  is no reset button or hold gesture. Do not reintroduce it without an explicit
  request.

## Data version

`RULESET_VERSION` + SDE stamp + ship attrs + module count + fallback KB IDs +
usage weights + weighted pool sizes feed `dataVersion`.

- Same SDE + same weights → stable version; no artificial progress reset.
- SDE/weights/pool changes feed `dataVersion`; the unfinished online state is
  keyed by the saved target/killmail, so a same-target rebuild does not reset
  progress. Stats/streak remain a separate localStorage key.
- Bump `RULESET_VERSION` for reveal/rules/scoring changes.

- `?claim=audit` selects Fitting Audit; `?claim=timed` selects Timed;
  `?claim=standard`, an absent claim, or any unknown value selects Standard.
- `?rule=audit`/`?rule=timed` remain for generated static share pages and are
  canonicalized to `claim`.
- `?kb=<opaque-token>` opens Free mode; only the current `k...` token format is
  accepted.
- `?mode=online` / `?mode=multiplayer` and `?room=<code>` are current app routes.
  Old `?mode=audit`, `?mode=timed`, `?timer`, `?timed`, `?lang`, `?free`, `?d`,
  `?killmail` and `?kill` are not read or migrated.
- Standard may omit `claim`; static share URLs still use `rule`.
- Standard, Audit and Timed are peer gameplay modes. Timed is not combined
  with Audit; its target source follows the selected Daily or Free mode.
- Puzzle state: `fitdle:v1:state:<date>:<mode>` (Timed uses `<mode>:timed`).
- Online run boards: `fitdle:v1:state:online-<runId>:<mode>` (finished ones are pruned);
  language:
  `fitdle:v1:lang`; font: `fitdle:v1:font`; font size: `fitdle:v1:font-size`;
  ESI type-name cache: `fitdle:v1:typeNames:<locale>`; zKill response cache:
  `fitdle:v1:zkill:*`; unsent online guesses: `fitdle:v1:pending-runs`; entity-name cache: `fitdle:v1:entity-names`; empty-hull
  setting: `fitdle:v1:allowEmptyKb`.
- Storage is origin-local; changing domain changes stats and saved language.

## Sharing

- Online Standard, Audit and Timed (including custom killmails) are not shared: their
  debrief has no share button or box. Online Daily, practice killmails and room
  invites are shared.
- Non-free share URL: `share/{1..6|lost}/{lang}.html` with optional `rule=audit`/`rule=timed`
  (no `kb`, `d`, `mode`, `timer` or `lang` query; the path locale controls preview
  language and is stored locally). Daily shares must not carry a reversible kill token.
- Free share URL: `share/free/{lang}.html?kb=...` with optional `rule=audit`/`rule=timed`.
  The preview redirects to the app without forcing a language.
- Timed share URL: `share/timed/{lang}.html?t=<seconds>&rule=timed`; Free Timed
  additionally carries `kb=...`.
- Opening a `kb` link compares its killmail with the current Daily target for the
  selected gameplay mode. On a match it enters Daily (restoring completed
  progress); otherwise it stays in Free mode.
- Static pages are generated per locale by `build-dist`; metadata is localized and
  contains only score/attempts, never the answer. The page stores its path locale
  locally before redirecting.
- OG images: `assets/share/og-{1..6|lost}-{locale}.png`, 1200×630, drawn as a
  closed Pend claim file: sender, status, a department line, score, review passes and a
  status stamp. All words come from `js/messages` and `assets/claim-departments.json`;
  the wreck is an invented outline, never a hull or killmail. `1` has a double stamp;
  `lost` is amber and its fragment 04 is missing.
- Regenerate with `uv run scripts/generate-share-images.py` (Windows fonts; uv provides
  Pillow). Raise the `?v=` in `build-dist`, `index.html` and the test when they change.
- `og:image` is score- and locale-specific, absolute using `PUBLIC_ORIGIN` or CI
  `PAGES_URL`; never commit a local domain.
- Cargo/type names not in SDE refs are fetched from the SDE record API
  (`<apiBase>/<release>/types/<id>.json`) with the current locale. Never reuse
  `extraTypeNames` across locales. Resolved names are cached in localStorage per
  locale (`fitdle:v1:typeNames:<locale>`). Audit representative selection itself
  is entirely local.

## Manual and legal

- The manual is now pure instructions plus the copyright/fan-work notice:
  Mode descriptions (Daily, Free), Gameplay descriptions (General, Standard,
  Audit, Timed), Multiplayer/Arbitration, then the legal notice.
- The multiplayer manual does not restate the solo gameplays: one block lists
  only how Standard/Audit/Timed rooms differ from solo, while Arbitration is
  explained in full. Manual bodies with several lines render as a list.
- Personal statistics, personal progress reset, language copy and display
  controls are not part of the manual.
- Display controls (font face, font size, empty KB) live in the compact Topbar
  gear menu. The 10th font-face click still enters the hidden Triglavian mode.
- Pilot records and logout live in the dropdown under the logged-in Pilot
  identity. There is no standalone Topbar logout button.
- Dossier layout: groups are balanced across two dynamic columns; equipment/cargo
  are not pinned to a column. The dossier header shows only the title; it has no
  subtitle sentence. Cargo capacity is the first row of the cargo group
  and keeps a labeled placeholder while hidden, including zero-cargo hulls.
- Newly revealed clues that are outside the viewport show a fixed edge arrow
  until the player scrolls them into view; clicking the arrow scrolls to the
  nearest unseen clue. Initial reveals also seed the unseen set when a fresh
  puzzle is opened with no guesses yet.
- A valid killmail whose victim hull is not in the catalog (for example a
  structure or container kill) shows the localized "signal unclassified" lore
  screen with a back button. It must not silently fall back to the daily target.
- The cargo group counter counts revealed cargo items only, excluding cargo
  capacity. It shows `revealed / ?` until every cargo item is revealed, then
  `X / X`; an empty cargo hold shows `0 / 0`.
- When a dossier equipment/cargo group has revealed rows followed by hidden
  rows, insert the `sealed-divider` line before the sealed row.
- After the answer is revealed, the wreck scan plate uses `object-fit: cover`
  so the image fills the viewport. Pre-reveal frames are randomized 32px hull
  renders with local crops and must never include the answer URL.
- Mass shows a fully written, non-abbreviated number by default in tonnes,
  using spaces as thousands separators and `t` as the unit. Clicking the mass
  row toggles between tonnes and kg; clicking again returns to tonnes. The kg
  state keeps the `kg` unit label. The mass row has no hover background effect.
- Manual shared rules are in `help.sharedRules` and appear under General.
  User-facing manual copy must stay abstract: describe the mode experience and
  guess behavior only; never expose queue names, budgets, weights, counts,
  thresholds, transfer formulas, or seed details.
- Mode sections must contain only mode-specific rules.
- Legal copy follows the ximicon.space CCP notice pattern, localized legally,
  with Fenris Creations (formerly CCP hf.) and the deployed site URL as the site
  subject. Never embed the repository URL in the legal copy.

## CI / deployment

- Home: https://github.com/steven-cmy/fitdle. CI is
  `.github/workflows/ci.yml` with jobs `sde-check`, `build`, `image`, `release`,
  `pages-build` (uploads the Pages artifact), `pages` (deploys it). Pull requests into `main` run `sde-check`, `build` (all tests) and
  `release-check` (`scripts/check-release.mjs`: for program changes, version newer
  than main and non-empty CHANGELOG section; see *Release notes*) only. `image`, `release`, `pages-build` and `pages` run only after a push to
  `main` (or a manual run on `main`); pushes to `dev` trigger nothing.
  `.github/workflows/reset-dev.yml` runs when a PR into `main` closes and resets
  `dev` after a merged `dev` PR (see *Version bump*).
- `image` builds the all-in-one image with `docker buildx` and pushes it to
  `ghcr.io/steven-cmy/fitdle`. Tags: version, `v`-version, `latest`, short SHA;
  `buildcache` holds the layer cache. On a push to `main` it pushes only when
  the GitHub Release `v<version>` does not exist, so published tags are not
  overwritten (it fails if that cannot be checked). A manual run on `main` always
  pushes, for example to rebuild with a new SDE, and overwrites the version tags
  and `latest`.
- `release` creates GitHub Release `v<version>` from the matching
  `CHANGELOG.md` section when that release does not exist yet; with no section
  it is skipped with a warning.
- `.gitlab-ci.yml` is the former GitLab pipeline (Kaniko into
  `registry.gitlab.com/cmy/fitdle`). The owner keeps it for now; do not delete it
  unless asked. Tests check the GitHub workflow.
- The published image is origin-neutral: Docker build uses
  `__FITDLE_PUBLIC_ORIGIN__`; the container entrypoint validates runtime
  `PUBLIC_ORIGIN` and renders it into static HTML before starting the service.
- The container entrypoint starts as root only to render `PUBLIC_ORIGIN` and
  create/chown the `DATABASE_PATH` parent and `/data` to `PUID:PGID` (default
  `1000:1000`), then drops to those IDs with `setpriv`. Bind-mounted and named
  volumes must be writable; read-only mounts fail fast. Unraid commonly uses
  `PUID=99`, `PGID=100`.
- `build-dist` adds one `?v=<version>-<hash>` to all script and stylesheet
  references, because CDNs may cache `.js`/`.css` while HTML stays fresh. The service
  caches those for long only when `v` is the version it serves.
- Do not restore the removed one-shot builder (`Dockerfile.oneshot`,
  `publish:builder`). The application is an online service, not a static site.
- The all-in-one `Dockerfile` builds SDE data and `dist/`, then runs
  `server/src/index.mjs` with `dist/`, `/api` and `/ws`. It needs `PUBLIC_ORIGIN`,
  `EVE_CLIENT_ID`, `EVE_CLIENT_SECRET` and `SESSION_SECRET` at runtime, plus a
  persistent `/data` volume for SQLite. Without `SESSION_SECRET` the server
  makes a random secret at every start, keeps it in memory only (nothing is
  written) and logs a red warning (plain text when stdout is not a terminal or
  `NO_COLOR` is set): every restart then signs everybody out, and the alternative,
  the default published in the source, would make the Daily predictable and
  sessions forgeable. Setting a fixed long random value ends the warning. Daily
  targets already stored in `daily_pins` are not affected by restarts.
- Boolean variables accept `1/true/yes/on` and `0/false/no/off` (any case); an
  unrecognised value warns at start and the default is used.
- The runtime image carries only the `data/` files the server reads, and links
  `/app/vendor` to `dist/vendor` for the server-side dogma engine. Update the
  `COPY` list when the server starts reading another file.
- `build-dist` writes `.br`/`.gz` siblings for static text assets (never HTML,
  which is rendered at container start) and per-language
  `dist/data/catalog/<locale>.json`; the browser falls back to the complete
  `data/catalog.json`. `FITDLE_SKIP_PRECOMPRESS=1` skips compression locally.
- `sde-check` compares the SDE API latest `release`/`buildNumber` with deployed
  `data/manifest.json`; writes `.cache/sde-check.env`.
- The build job compares the latest SDE release with its cached `sde-meta.json`
  and skips `prepare:sde` when they match and normalized schema version 3 is
  cached; a schema/SDE change or `FORCE_SDE=1` downloads the SDE again.
- Build caches (via `actions/cache`, a new key per run) `.cache/normalized.json`, `.cache/killpool.json`,
  `.cache/sde-meta.json`, `.cache/ship-usage.json`, `.cache/zkill-version.json`
  and passes them to `image` (`REUSE_BUILD_CACHE=1`), so the image makes
  no data requests and matches Pages. Other image builds fetch everything.
- If `data/catalog.json` is missing, build the catalog first; the kill pool needs it.
- Daily scheduled pipeline is disabled: daily selection no longer depends on a
  rebuild. Builds run on pushes to `main`, pull requests into `main` and manual runs; only `main` publishes.
- `pages` deploys `dist/` to GitHub Pages
  (https://steven-cmy.github.io/fitdle/; repository setting Pages → Source:
  GitHub Actions). Pages is practice/static-only; online login, scoring and rooms
  require the all-in-one service.
- Production: `fitdle.itworks.cc` runs the all-in-one image on the owner's
  Unraid Docker host; the owner pulls new images manually. Cloudflare Insights
  injected there is not app code.
- The repository URL used in User-Agents and the footer is set in
  `server/src/config.mjs` and `scripts/build-catalog.mjs` (plus the other
  `scripts/*` User-Agents).

## Known limitations

- SDE builds require network access to `sde.evetech.net`; a complete cached
  `.cache/sde-source` can build offline. The latest release can change more often
  than the old zip, so use `check:sde-cache`/CI `sde-check` rather than rebuilding
  blindly.
- zKill can rate-limit; a ship-page failure aborts target selection instead of
  silently falling back to a static pool or another ship.
- Dogma cannot recover the victim's real skills/mutations; it simulates all-V and
  active modules.
- Cargo/type names absent from local refs use the SDE record API; a network
  failure keeps the numeric fallback and does not block the puzzle.
- The online service is single-instance with SQLite. Rooms are authoritative in
  memory with DB snapshots; there is no horizontal scaling or public leaderboard.
- GitHub Pages publishes only the static/practice build. Online login, scoring and
  rooms require the all-in-one Node service.
